DeckRPG Engine Plan – Suggested Improvements

These are refinements and additions to the current architecture plan.
None of these are required immediately; they are meant to strengthen the
design while keeping the system simple and scalable.

  -----------------------------------
  1. Rename Runtime → EngineRuntime
  -----------------------------------

Reason: The name “Runtime” is vague and may become confusing later if
the project grows.

Recommended structure:

Sources/ CoreAPI/ UI/ Graphics/ EngineRuntime/

Why this helps: Future tooling may include multiple runtimes such as: -
EditorRuntime - ServerRuntime - ToolRuntime

Naming it EngineRuntime clarifies that this is the actual game runtime
implementation.

  -------------------------------------------
  2. Maintain a Strict Dependency Direction
  -------------------------------------------

Recommended dependency graph:

CoreAPI ↑ UI

CoreAPI ↑ Graphics

CoreAPI + UI + Graphics ↑ EngineRuntime

Key rule: UI should never depend directly on Graphics or SDL.

Instead it should depend on small interfaces such as:

UIRenderer InputProvider AssetLoader EventBus TimeProvider

EngineRuntime implements those interfaces and injects them at startup.

This keeps UI portable and prevents engine details from leaking upward.

  -------------------------------------------
  3. Introduce an InputProvider Abstraction
  -------------------------------------------

Purpose: Insulate the rest of the engine from SDL input types.

Flow:

SDL ↓ SDLInputProvider ↓ InputProvider API ↓ Engine systems

Example API:

pollEvents() nextEvent() isKeyDown() isMouseDown() mousePosition()

Benefits: - SDL stays isolated in one module - Easier platform changes
later - Replay systems become possible - Easier automated testing

  ----------------------------------
  4. Add a Small InputRouter Layer
  ----------------------------------

Purpose: Control which systems receive input events.

Flow:

InputProvider ↓ InputRouter ↓ ScreenManager (UI) ↓ Gameplay systems

Routing rule:

UI receives input first. If UI consumes the event, gameplay does not
receive it.

This avoids input conflicts between UI and the game world.

Note: This layer can initially be very small and expanded later.

  ------------------------------------------
  5. Add Action Mapping for Gameplay Input
  ------------------------------------------

Instead of gameplay code checking keys directly:

Bad:

if input.isKeyDown(.w)

Good:

if input.isActionDown(.moveForward)

Example actions:

MoveForward MoveBackward Jump Interact Shoot

Benefits:

-   Easy key rebinding
-   Keyboard + controller support
-   Multiple bindings per action
-   Cleaner gameplay code
-   Decouples gameplay from hardware devices

UI should still use raw input events.

Gameplay should use actions.

  ----------------------------------------------
  6. Introduce a Small Frame Context Structure
  ----------------------------------------------

Instead of passing many services around, introduce a frame context:

Example:

FrameContext - time - input - renderer

This keeps frame data centralized and simplifies function signatures.

Typical frame loop:

dispatcher.flush()

input.pollEvents()

inputRouter.processEvents()

screenManager.update()

screenManager.render()

  ---------------------------------
  7. Keep CoreAPI Extremely Small
  ---------------------------------

CoreAPI should contain only lightweight protocols such as:

UIRenderer InputProvider AssetLoader EventBus TimeProvider JobSystem

Rule of thumb:

CoreAPI should remain small and stable. It defines interfaces, not
implementations.

Implementations belong in EngineRuntime.

  ------------------------------------
  8. Start with a Minimal Job System
  ------------------------------------

Recommended MVP job system:

thread pool job queue completion queue main thread dispatcher

Basic API:

enqueue(job) enqueue(job, completion) dispatchToMain() JobHandle
JobCounter

Rules:

Worker threads must never call: - SDL - UI APIs - Rendering APIs

Workers post results to the main thread dispatcher instead.

  ----------------------------------------------
  9. Separate Raw Input from High-Level Events
  ----------------------------------------------

Raw input events:

KeyDown KeyUp MouseMove MouseDown MouseUp

High-level events:

UIAction.StartGame PlayerDied InventoryItemAdded

Rule:

Raw input goes through InputProvider + InputRouter.

Meaningful gameplay events go through EventBus.

  ----------------------------------------
  10. Defer Complex Systems Until Needed
  ----------------------------------------

Do NOT add early:

-   complex input device hierarchies
-   advanced UI layout engines
-   large event frameworks
-   complicated job scheduling

Start simple and expand when the game actually requires it.

------------------------------------------------------------------------

Summary

The key architectural principles:

• isolate SDL behind InputProvider • keep UI dependent only on CoreAPI
interfaces • route input through a controlled path • use action mapping
for gameplay input • keep CoreAPI small and stable • keep worker threads
away from UI/SDL • design systems that can grow later without major
rewrites

This preserves simplicity while keeping the engine flexible for future
growth.
