DeckRPG Engine – Recommended Structure and Dependency Graph

This document summarizes a clean project structure and dependency layout
based on the current engine design goals.

The main objective is to keep systems modular, minimize coupling, and
ensure that high‑level systems do not depend on platform details.

  -----------------------------------------
  1. Recommended Project Folder Structure
  -----------------------------------------

Sources/

  ----------------------------
  2. Module Responsibilities
  ----------------------------

CoreAPI

Purpose: Defines small engine-facing protocols and shared types.

Examples: - InputProvider - UIRenderer - JobSystem - EventBus

Rules: • Only interfaces and small data structures • No SDL • No
rendering backend • No platform code

UI

Purpose: Implements retained-mode user interface.

Contains: - ScreenManager - Screens - UI components (Button, Panel,
etc.) - Layout definitions

Dependencies: UI depends only on CoreAPI protocols.

UI must never directly reference: - SDL - renderer implementation -
platform APIs

Graphics

Purpose: Rendering data structures and renderer APIs.

Examples: - Renderer - textures - meshes - font atlases

This module represents the engine’s rendering layer but should still
remain independent of platform windowing.

EngineRuntime

Purpose: Concrete runtime implementation.

Responsibilities:

• bootstrapping the application • implementing CoreAPI protocols •
connecting systems together • handling SDL interaction • running the
main loop

Examples:

SDLInputProvider EngineUIRenderer JobSystemImpl MainThreadDispatcher

  ---------------------
  3. Dependency Graph
  ---------------------

The dependency direction should always point upward.

CoreAPI ↑ UI

CoreAPI ↑ Graphics

CoreAPI + UI + Graphics ↑ EngineRuntime

Important rule:

High level systems must not depend on low level implementations.

Example:

UI → UIRenderer (interface)

EngineRuntime → EngineUIRenderer → actual renderer

This allows the UI module to stay decoupled from rendering details.

  -----------------------
  4. Example Frame Loop
  -----------------------

A typical main loop might look like this:

dispatcher.flush()

input.pollEvents()

inputRouter.processEvents()

screenManager.update(deltaTime)

screenManager.render(renderer)

renderer.present()

This ensures:

• main-thread safe UI and SDL usage • job completions are processed
first • input is routed before updates

  ---------------
  5. Input Flow
  ---------------

Input should follow a controlled path:

SDL ↓ SDLInputProvider ↓ InputEvents + InputState ↓ InputRouter ↓
ScreenManager / UI ↓ Gameplay systems

Gameplay code should usually read from action mapping:

isActionDown(.moveForward)

instead of checking physical keys directly.

  --------------------
  6. Job System Flow
  --------------------

Worker threads execute heavy tasks:

asset decoding text shaping atlas generation background loading

Workers must never call:

SDL UI code rendering APIs

Instead they push completion tasks:

worker thread ↓ completion queue ↓ MainThreadDispatcher ↓ executed at
start of frame

  ----------------------
  7. Design Principles
  ----------------------

The engine architecture follows several core principles:

• Dependency inversion • Platform isolation • Main-thread safety • Small
interfaces • Expandable systems

This keeps the engine flexible while avoiding premature complexity.
